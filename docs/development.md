# Development Guide

This repo is a local one-user, stdio-only Clockify MCP server. Keep new work in
that shape: one pinned workspace, descriptor-first tools, workflow tools first,
domain tools second, raw fallback last.

## Adding Or Changing A Tool

1. Start with the descriptor in the existing domain file. Keep the input schema
   strict and leave `additionalProperties:false` in place after normalization.
2. Set the right MCP hints and risk metadata. Billing, admin,
   permission-change, external-side-effect, and destructive tools must be
   represented in `RiskClass`; add or adjust `risk_overrides.go` when the
   default read/write/destructive hints are not precise enough.
3. Add `dry_run` behavior for writes. If a high-risk tool cannot provide a rich
   handler preview yet, the central dispatcher supplies a no-upstream preview
   and `confirm_token`; do not bypass confirmation to make a test pass.
4. Validate aliases or alternatives before the Clockify client is called. For
   example, `category`/`category_id` and `policy`/`policy_id` pairs must fail
   locally when neither side is supplied.
5. Every write result should include useful IDs and a clear `changed` summary.
   Recoverable failures should return `ok:false`, a stable error code, and
   recovery guidance.
6. Add focused fake-upstream tests proving dry runs do not mutate and invalid
   argument combinations fail before upstream. Add live evidence only under the
   gates documented in `docs/live-tests.md`.

## Generated Surfaces

After descriptor, schema, risk, or output-shape changes, refresh generated
surfaces through the repo commands, not by hand:

```sh
make gen-tool-catalog
bash scripts/check-api-parity-matrix.sh --write
make gen-raw-allowlist
make sync-selfinspect-assets
```

Then run the matching drift checks:

```sh
make catalog-drift
make api-parity-matrix-drift
make raw-allowlist-drift
make selfinspect-drift
```

Do not hand-edit `docs/openapi/clockify-openapi.yaml`; it is generated by
`scripts/gen-clockify-openapi`.
